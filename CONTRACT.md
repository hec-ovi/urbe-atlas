# CONTRACT: atlas

Purpose: deterministically generates the 2D city blueprint (districts, streets with sidewalks, typed parcels with 3D envelopes, transit and optional hydrology) from a seed and parameters.

Status: package v0.4.0, blueprint v0.18.0. Breaking changes go through the orchestrator.

## Conventions
- Units: meters. Ground plane XZ, +Y up. 2D points are `[x, z]`; heights along +Y.
- Polygons: CCW rings, first point not repeated.
- Determinism: same seed + params, byte-identical blueprint JSON.
- IDs: deterministic strings with a disjoint prefix per collection: `d` district, `n` street node, `e` street edge, `b` block, `p` parcel, `bs` bus stop, `br` bus route, `ts` train station, `tl` train line, `ss` subway station, `sl` subway line, `w` water body, `sh` shoreline and `ws` water structure.

## In
`generateCity(params: AtlasParams, onProgress?: ProgressObserver): CityBlueprint`

The optional observer receives completed pipeline stages and the current phase, [schema/progress.ts](schema/progress.ts). Counts measure completed stages, not elapsed time; serialized worker results complete the final stage. The blueprint and deterministic geometry are unchanged by observation.

Params: [schema/params.ts](schema/params.ts). Only `seed` is required; every other field has a documented default (size, district count range, max floors global and per district kind, wealth tier weights, feature toggles for highways, trains, subways, alleys, air and underground tunnels). `hydrology: { type }` optionally selects `lagoon`, `river`, or `sea-coast`; omission means no water and adds no output field.
`streetDesign` supplies numeric road and sidewalk profiles, [src/streets/construction/schema/design.ts](src/streets/construction/schema/design.ts). Omission selects 1/2/4 lanes at 4/7/14 m and 2/4/6 m paved sidewalks, with an additional 0.2 m curb and 0.3 m gutter per side. Explicit street profiles may have 1 or 2 lanes; avenues have 4. Profiles are selected before land subdivision. Saved blueprints retain their authored dimensions.
`pavingDesign` optionally supplies caller-selected finish family IDs, module pitches, joints and district layout overrides, [src/streets/construction/paving/schema.ts](src/streets/construction/paving/schema.ts). It is validated before generation. The city selects finish families from this input; physical dimensions come from the module catalog. Atlas imports no material assets.
`footprintShape` defaults to `rectangle`; explicit `parcel` follows the setback-adjusted lot shape. Rectangles use the shared half-metre construction grid and the same hosting policy for use eligibility and final buildability.
Nested parameter objects and arrays are validated at runtime. Unknown district kinds, wealth tiers and feature names, non-boolean toggles, malformed ranges and non-finite numbers fail with `E_INVALID_PARAMS`. Browser parameter imports apply the same validation before changing the form.

CLI: after `npm run build:cli`, `npm run generate -- --seed <seed> --out <file.json> [--size N] [--irregularity X] [--max-floors N] [--no-highways] [--no-trains] [--no-subways] [--no-alleys]` executes the prepared artifact without modifying the Atlas package and writes the blueprint JSON only to the requested path. Exit 1 on AtlasError (code printed), 2 on usage error. `npm run preview` prepares the same CLI before its server starts.

Build: `npm run build` type-checks the package, writes the CLI to `dist/cli.mjs`, the city worker to `dist/city-worker.mjs`, and the browser preview under `dist/preview/`. `build:cli` and `build:cities` prepare their individual entries. Preview startup prepares both Node entries. Each build preserves the other outputs.

Preview hosting mounts the [city catalog API](src/cities/CONTRACT.md) on the same origin in development and production preview. `ATLAS_CITY_DATA_DIR` defaults to `.atlas-cities` relative to the server working directory. Blueprint generation runs in a worker; saved cities persist there. Exterior and interior generation remain separate stages. The browser consumes this API through the [UI contract](src/ui/CONTRACT.md).

Root construction entries:

- `JunctionGround.plan(input)` / `.build(input)` in [JunctionGround.ts](src/streets/JunctionGround.ts) take [JunctionGroundInput](schema/junction-ground.ts): one isolated, flat, straight, axis-aligned through-avenue T, its original source contact, matching Datum roles and runs, explicit bottom, setback and station pitch. All six sides have the same role intervals and levels. They return the retained source ground plan or its snapshot, with distinct roadway, lip, gutter, curb and paved roles. Other junction topologies, bends, unequal side profiles and grade transitions fail with `E_INVARIANT`; insufficient full-width return land or arm length fails with source evidence. This entry does not activate modern city generation.
- Junction returns share cumulative beveled boundaries and original authored support references. Straight handoffs follow the original run's station phase; widths never shrink. Source claims outside the return domain retain their Datum masks, IDs and levels. Junction sources retain contact/group/node/edge/span provenance. One retained partition assigns every positive-area piece; no exported boundary rebuilds ownership. Input order and repeated calls preserve output bytes. Paving, ramps, materials and render encoding remain separate consumers.
- `JunctionGround.fitting(input)` returns [JunctionFittingConstruction](schema/junction-ground.ts): six original-arm/side fields, source IDs, shared run frames, original handoff stations and two corner transition supports. Exact authored-1mm field intents cover each referenced junction role once within its retained owner; they are not replacement ground. Corner supports define infinite lines for continuous transition joints across paving, curb and gutter; their incident run phases need not coincide. Consumers extend layout-width joint strips beyond owner bounds, reserve them first, then fit cells inside the remaining fields. Opposite-frontage fields share one through-run phase with no extra seam. Every remaining piece keeps its exact owner boundary. This pure entry changes no source or ground snapshot; unsupported sources use `E_INVARIANT`.
- `CityConstructionSupport.assert(design)` in [CityConstructionSupport.ts](src/CityConstructionSupport.ts) accepts resolved profiles with whole-metre carriageway totals, paved widths 2/4/6 m, curb width/rise 0.2 m, gutter width 0.3 m and lip width/height 0.02 m. Unsupported profiles fail before generation with `E_INVALID_PARAMS`, the field, profile ID and `supportedFormat: modules`.
- `GroundCover.plan(input)` takes legacy [GroundCoverInput](src/streets/GroundCoverSchema.ts) (boundary, water, station bays and surface masks) on the authored 1 mm grid. It returns a runtime-only `GroundCoverPlan`: one opaque exact partition, original boundary, coordinate scale, semantic owner IDs/levels and excluded owner IDs. Ordered legacy ownership is water, station bay, roadway, curb, sidewalk, block, open, then open fringe. Empty semantic owners remain listed.
- `GroundCover.snapshot(plan)` returns shared-vertex `GroundSurface[]` after verifying the partition. The numeric view does not replace or consume its exact state. Snapshot metadata must describe every nonexcluded current owner; unknown owners fail. A fitting consumer can refine those retained handles and publish its own final view.
- `GroundCover.build(input)` composes `plan` and `snapshot`. Off-grid input, inconsistent snapshot metadata and partition errors use `E_INVARIANT`. Ground construction imports no paving implementation, and retains no second owner-polygon cache.
- The same entries accept `format: 'source-claims-v1'`, [source schema](schema/ground.ts), with an authored boundary, excluded land, complete source claims and explicit open remainder. Each source has a unique caller-owned ID, absolute bottom/top and geometry-free street-side, roadway, junction or land provenance. Gutter and gutter-lip are distinct surfaces; other paved functional roles retain sidewalk surface. No modern height comes from legacy ground levels.
- Modern `plan` returns [SourceGroundCoverPlan](src/streets/GroundCoverSchema.ts). Modern `snapshot`/`build` returns `{format, sources, ground}`; every ground record references its source and has the same surface/levels. Subdivision retains source IDs. Metadata is copied; source masks are not a published geometry cache.
- Complete source claims must fit the city minus excluded land and have mutually disjoint interiors. Overlapping masks within one claim form that source's union. Distinct claims cannot resolve an overlap by order, even with equal roles or heights. Out-of-domain claims, conflicting ownership, duplicate IDs, invalid provenance/levels and inconsistent source references fail with `E_INVARIANT` and source evidence. Empty claims and boundary-only contact are valid.
- An empty modern claims list establishes the retained land partition with its explicit open owner. A later construction stage can divide those same owner handles through the partition contract and register matching source/owner metadata before snapshot. Complete raw masks can enter a retained subdomain directly; exported numeric boundaries never rebuild ownership. This entry does not construct junction returns or accept unresolved junction overlaps.
- Source-owned snapshots are an additive construction shape, separate from `CityBlueprint`. City, paving and movement consumers require their own format negotiation before using these roles and heights.
- `CityCrossings.plan/validate`, [CityCrossings.ts](src/CityCrossings.ts), takes orthogonal street nodes/edges, final ground and physical obstacles and publishes [crossing records](schema/blueprint.ts). Each eligible junction arm has a 3 m field with whole 0.5 m stripes, complete roadway coverage and sidewalk walking terminals. Continuations and motorway arms have no crossings. Validation rebuilds required records, so saved omissions or altered geometry fail with `E_INVARIANT`.

Saved examples live in `samples/`; their metadata identifies the format they contain.

## Out
`CityBlueprint`: [schema/blueprint.ts](schema/blueprint.ts).
- `meta`: schema version, seed, resolved params, bounds, city grid angle, rectangular city boundary polygon and `buildingGrid: {origin: [0,0], angle: gridAngle, spacing: 0.5}`. Grid angle is radians; coordinates and spacing are metres.
- `districts`: kind (downtown, commercial, residential, industrial, mixed), wealth tier, boundary (a rectangle on the city grid, clipped to the city outline), floor cap.
- `streets`: planar graph of nodes and edges; each edge has class (`street` | `road` | `highway` | `alley`), centerline path (straight row and column segments), carriageway width, per-side sidewalk widths, and an `elevationProfile` of `{ distance, level }` knots measured along its own path. `level` remains the flat or maximum height (0 at grade, 8 on a highway deck, [src/levels.ts](src/levels.ts)). Node `connections` group incident edges by their endpoint level, and a vehicle transfers only inside one group, so a grade road does not connect to the highway crossing above it. The graph also carries pedestrian crossings. Each crossing segment names its street edge, connects the two sidewalk walking bands, has a 3 m width, and publishes fitted 0.5 m zebra stripe polygons over the carriageway. Traffic signals have one head per junction arm with the mast that carries it. `planting` is one flat list of street furniture points for the whole city, each with its `edgeId`, its `kind` (`tree` | `pole` | `bin`, a closed set: skip a kind you do not know rather than draw it wrong) and the spacing its stretch runs at. `highwayStructures` has one construction record per maximal highway run with its ordered edge IDs, continuous path, width, level, deck thickness, ramp lengths, matching elevation profile and support columns.
- `blocks`: grade-street-bounded faces with a curb strip, sidewalk strip polygons, contained parcels and open areas. `boundaryRegions` owns exact block land as disjoint simple pieces; `boundary` is its enclosing compatibility outline. Hole-partition cuts share one block identity and create no frontage. Curb corners at intersections carry a rounded return.
- `streets.construction`: ordered through-runs with stable `sr` ids and path distances, [src/streets/construction/schema/sections.ts](src/streets/construction/schema/sections.ts). Grade edges publish `crossSection`: exact lane offsets and separate left/right curb, border, furnishing, walking and frontage bands. Scalar widths equal these totals. Highway dimensions retain their structure contract. Crossing `roadway` endpoints describe the marking span separately from unequal pedestrian approaches.
- `streets.construction.planningReservations`: exact edge-local roadway, left/right sidewalk and walking polygons with their directed sweep model, [src/streets/construction/corridors/CONTRACT.md](src/streets/construction/corridors/CONTRACT.md). These planning queries include bends and caps. Final ground polygons apply junction, elevation and water ownership; a reservation is not an alternate render or collision surface.
- `streets.construction.modules`, [module schema](src/streets/construction/modules/schema.ts), publishes reusable physical prism definitions and repeated quarter-turn placements. These prisms own street rendering and collision, including panel joints, gutters, guardrails and parking returns. Ground records marked `moduleBlockId` are compact planning covers. Optional frontage owners describe the continuous outer sidewalk. Saved fitted paving uses its [own contract](src/streets/construction/paving/CONTRACT.md).
- `parcels`: type (residential, hotel, offices, corpo, hospital, clinic, police, military, factory, commerce, mall, restaurant, coffee_shop), tier (poor, mid, rich, high_rich), lot polygon, footprint polygon, street access point and 3D envelope (min/max floors, nominal floor height and max height; real per-floor elevations are owned by Exterior). A default footprint is a complete grid-aligned rectangle inside its setback land. It satisfies the type's minimum band and core fit; unused land remains part of its lot. Explicit `parcel` footprints follow the inset lot and required band.
- `transit`: bus stops and routes over street edges; train and subway stations and lines, each with its `level` (trains at grade, subways at -12 m) and full corridor `width` (4 m train bed, 6 m subway tunnel diameter). Rail paths advance without an immediate reciprocal segment. A station publishes its platform polygon and vertical box (5 m headroom underground, 3 m at grade), street-level entrances, and underground shafts and `accessPaths`. Subway `entranceBays` name each directed street side, full reserved land, shaft and walking-band approach, [src/transit/reservations/schema.ts](src/transit/reservations/schema.ts). `subwayDemand` records the pre-parcel population forecast and line target. Each line ends inside its terminal platforms. An access path is ordered `[x, y, z]` centerline data: switchback stairs inside the shaft, then a level passage to the platform. Grade stations publish neither shafts nor access paths.
- `hydrology` (optional): [src/hydro/schema/hydrology-plan.schema.json](src/hydro/schema/hydrology-plan.schema.json). It publishes independent `seedId`, water surfaces, shoreline paths and water-side construction bands, elevation, depth, material key and bridge/tunnel contacts. A structure's optional `corridor` is its exact wet-contact reservation; `path` locates that contact along the source network and `width` remains metadata. The source network owns the complete deck or tunnel geometry. Renderers consume water `surfaces` at `elevation`, shade to `depth`, resolve `materialKey`, and draw shoreline `path` and `band`.
- `volumetric`: one prism per parcel plus disjoint planning ground (roadway, curb, gutter, sidewalk, block, open). Module-city levels are roadway -0.2..0 m, gutter -0.03..0 m, curb -0.03..0.2 m, and sidewalk/block/open 0..0.2 m. Physical module prisms retain their exact joints and lip heights. Water is published separately.
- `stats`: population estimate, parcel counts per type, per district.

## Errors
Closed set, thrown as `AtlasError { code, message, details? }` ([schema/blueprint.ts](schema/blueprint.ts)):
- `E_INVALID_PARAMS`: params fail validation; message names the field.
- `E_UNSATISFIABLE`: params cannot yield a coherent city (e.g. size too small for the district count, or below 420 m on one axis when hydrology is requested).
- `E_INVARIANT`: post-generation coherence check failed; atlas bug, report with seed and params.

## Invariants
- Rectangular hosting maximizes whole-cell area, then short-side width, then lower grid coordinates and wider U dimension. Full transformed lattice coordinates preserve each building corner; analytic containment checks the complete rectangle against its setback land, allowing only floating-point transform roundoff. Ineligible lots use the existing lighter use, neighbor merge or open-land policy; no rectangle is clipped into an irregular building.
- Bus stops keep the researched spacing in a city 1.6 km across or larger and close in proportionally below that, so a small city still runs routes. Route search uses node and endpoint level as one state. Every consecutive edge pair shares a node and belongs to the same `connections` group at that node, so a bus cannot transfer between a grade road and the highway deck above it.
- Street intersections are shared row/column identities. Each row and column has a fixed road profile. Rectangular blocks contain whole 2 m panel groups and fixed corner modules. Seed variation changes complete panel counts and profile choices.
- Streets, districts and building grids follow world X/Z axes. The city boundary is rectangular. `irregularity` is accepted in [0, 1] for saved parameter compatibility, defaults to 0, and does not alter module-grid geometry. The current grid contains no diagonal or alley cuts.
- The [street layout](src/streets/layout/CONTRACT.md) reserves lane widths, complete block panels and outer sidewalks directly within the requested extent. Building parcels use the remaining block interiors.
- Districts use axis-aligned cuts between planned centers and remain rectangular within the city boundary.
- Levels are the one place height lives for networks: a consumer reads street height by linearly interpolating its ordered elevation profile, and stacks flat tracks and platforms from `level`, never from class. Every street profile starts at distance 0, ends at the exact 2D path length, has strictly increasing distances and stays within 0 and its declared maximum level. Every non-highway profile is flat. Node connection groups contain every incident edge exactly once and only join equal endpoint levels.
- A highway is a through route: every highway chain ends either at a junction with other highway arms or within 30 m of the city boundary, so a deck never dead-ends over a block. A chain that stops inside the city or cannot hold its ramps plus a supported flat span is demoted to `road` before widths and blocks are read. When tracing leaves no usable highway, the shortest graph route between the farthest city-edge nodes becomes one complete route before blocks and parcels are derived.
- Every highway edge belongs to exactly one `streets.highwayStructures` record. Its ramps rise linearly from grade to the 8 m deck over 60 m only at city-edge termini, shortened only when the whole run is shorter. The structure and its routing edges publish the same height knots, including a breakpoint when a ramp ends inside an edge. Its 2 x 2 m supports stand under the flat deck at no more than 30 m intervals, from ground to the deck underside; a support moves across the deck or shifts the pitch backward where grade infrastructure crosses it. Each shift is bounded by the preceding support, so placement always advances or fails with `E_INVARIANT`. Decks keep 1 m of construction clearance beyond each edge from every building footprint. Support footprints never enter a building footprint, grade rail corridor, subway entrance shaft, curb or sidewalk. All support centers are on the 1 mm coordinate grid.
- Highway construction supports an early envelope stage and later support placement, [src/streets/construction/highway/CONTRACT.md](src/streets/construction/highway/CONTRACT.md). The edge-only envelope contains every final structure field except supports. Support completion preserves that envelope exactly; the combined entry point remains available. Assigned routing profiles are checked against the shared run height function.
- IDs are globally unique across the whole blueprint (disjoint prefixes per collection).
- Street graph is connected; every parcel's access point lies on a sidewalk of its access edge.
- Every edge is a real run of street: its two nodes differ, no path point repeats, and no vertex turns more than 120 degrees. A sharper turn would fold the edge's sidewalk band back over its own roadway.
- A physical street path appears once per source family, independent of direction or collinear subdivisions on the coordinate grid. Street and road traces share a family with road precedence; highways and pedestrian alleys have separate families.
- Initial graph normalization resolves same-endpoint, same-family paths at the configured node snap radius. Both paths must advance strictly along their common endpoint chord and stay within that radius at every shared projected station. Returning paths and separated parallels remain distinct. Canonical order is class precedence, shorter length, then whole-path grid key; each removed path matches a retained representative directly. Extension uses exact identity only.
- `StreetGraphBuilder.build` and `extend`, [graph types](src/streets/Graph.ts), route target paths through accepted source endpoints before detecting intersections. A terminal is accepted only when the target segment visits its half-open 1 mm grid cell and the routed segments stay in the reserved domain. Accepted contacts on one target segment sort by projected station, then X and Z. The complete composed path must remain covered by the domain or fail with `E_INVARIANT`; accepted contacts are not discarded. Each terminal is one logical contact at its source coordinate before configured graph normalization; separate authored terminal cells and intersections remain distinct.
- `StreetGraphBuilder.extend(existingGraph, newLines, {domain})` adds traced paths to the current graph without simplification or radius clustering. Existing coordinates and accepted terminal coordinates remain fixed. Graph normalization and stable ID assignment run over the combined network.
- `StreetGraphBuilder.build(lines, {simplifyTolerance, snapRadius, domain})` accepts zero `snapRadius` for exact node identity without endpoint movement or distance-based path merging. Contact-cell routing and source-path simplification retain their existing rules.
- Initial graph simplification retains every source endpoint shared with another source path as a required anchor. Only exact shared coordinates establish these authored joins.
- Sidewalks connect through complete external crossing approaches, [construction contract](src/streets/crossings/CONTRACT.md). Original node connection groups retain their identity inside each physical junction. Positive-width external grade arms with both sidewalks publish one field each; pedestrian alleys and highways publish none. Whole 0.5 m stripes repeat inside a 3 m field with equal margins. Crossing-only connectors can include the unmarked road margin; terminal strips must fit actual pedestrian ground and their declared walking bands. Complete fields avoid intersecting traffic and physical obstacles under the caller's pedestrian-clearance setting. Derived cuts retain their shared source-edge interpolation coordinates.
- Traffic signals use each physical junction's external approach cuts. A junction with three or more grade motor arms, including at least one road, carries one head per arm, or none. Highways and pedestrian alleys carry no head. A pole stands in its approach's furnishing band (right-hand traffic); `facing` looks back down the arm and `mast` reaches square to it across the approach lanes to the roadway centerline. Heads stand at the exterior boundary of the complete crossing field.
- Street furniture stands in the kerb-side furnishing strip of a sidewalk, never in the walking line: 8 m apart in downtown and commercial districts, 12 m elsewhere ([src/streets/Planting.ts](src/streets/Planting.ts)), a light pole every third point, and always 6 m clear of a crossing, a bus stop, a station entrance and a parcel access point. Streets and roads carry it; an alley has no kerb and a highway no sidewalk.
- Every stop and station belongs to a route or line serving at least two stops or stations. Rail networks are connected and contain no immediate double-back. Subway endpoints lie inside their terminal platforms; an insufficient route or unavailable entrance land fails with `E_UNSATISFIABLE`.
- Grade rail and subway entrance bays reserve land before parcels. Train beds and platforms keep 1 m of building clearance; platforms also avoid the highway deck corridor. Each subway shaft is 8 by 3 m with a 1 m apron outside the complete sidewalk. Its approach starts in the authored walking band, whose width remains clear. Bay footprints receive sidewalk paving and exclude parcel lots. The early subway plan uses the zoning population forecast and survives final population changes unchanged. Grade infrastructure and subway shafts stay clear of highway supports.
- A station is walkable end to end: its platform is a simple ring covering the station's position; underground it carries one shaft and one access path per entrance. The stair centerline descends through four non-vertical switchback flights inside its shaft, its passage stays at platform level, every leg joins exactly, and the final handoff lies inside the platform. An underground entrance is at most 30 m from its platform: NFPA 130 caps the walk from the platform's most remote point to the street at 100 m, and half a 140 m platform takes 70 of them. Platform sizes are researched ([src/transit/stations.ts](src/transit/stations.ts)): 140 x 8 m metro island, 180 x 6 m regional.
- Parcels never overlap; parcels, curb, sidewalk and open areas cover their block's `boundaryRegions` (or legacy `boundary`); ground surfaces cover the city without gaps.
- Module support covers are constructed once per template and placed by their shared transforms. Road rectangles, module covers, lots, station paving and open land cover the city without positive-area overlap. Station additions exclude existing pavement and their land is subtracted from lots and open areas.
- Each paved sidewalk is 2, 4 or 6 m wide. Curbs are 0.2 m wide and high; gutters are 0.3 m wide with a 0.02 m lip. Straight panels are 1 m squares with 12 mm modeled joints, with optional 2 m middle groups on wider sidewalks. Standard rounded corner radius is 2 m. Side reservations add curb and gutter outside the paved width.
- Block and ground polygons are simple rings with positive area. Wide frontages may carry sparse 4 x 2 m parking slots with 2 m terminal returns and at least 2 m of walking width. Guardrails use repeated 2 m modules with corner and parking clearances.
- Feature toggles are respected: a disabled feature produces no entities of that kind.
- Hydrology is derived from its independent seed stream before infrastructure placement. Water surfaces and shorelines are bounded, snapped to 1 mm, CCW, simple and byte-stable. Parcels, accesses, stations, entrances and land cover avoid water. A network touches water only inside its typed bridge or tunnel contact; constructed street contacts include both actual sidewalk widths. Highway supports in water belong to a published highway bridge.
- Every parcel footprint hosts the core rectangle its type needs, derived from interior's published core feasibility ([src/zoning/core.ts](src/zoning/core.ts) mirrors the constants of `../interior/schemas/core-feasibility.json`; a test fails when that file moves). A rectangle is a core mode's band length by its plate depth, with the stair shaft sized for the longest flight the recipe allows, plus one 0.5 m snap (the corridor face and the core start land on interior's grid) and twice the deepest facade (0.62 m) on both axes; it fits in either orientation. Walkup 11.14 x 9.74 m, walkup with two stairs 17.64 x 9.74 m, compact elevator core 12.14 x 13.74 m, standard elevator core 20.14 x 9.74 m. A heavy type (offices, corpo, hotel, hospital, mall, factory) hosts the compact rectangle; a light type (residential, commerce, restaurant, coffee_shop, clinic, police, military) hosts the walkup rectangle, and one of the two-stair rectangles when its footprint exceeds 460 m2.
- Every parcel footprint keeps its type's band end to end, the short side of its rectangle: `HEAVY_BAND` 12.14 m, `LIGHT_BAND` 9.74 m ([src/zoning/bands.ts](src/zoning/bands.ts)). The band is the width between the footprint's two long sides along the whole footprint, where an oblique end cut is a cap and not a narrowing. The zoner assigns a lot only types whose band it hosts; a heavy type whose footprint cannot host its rectangle is retyped to the district's main light type (commerce in downtown, commercial and industrial districts, residential in residential and mixed ones); a lot hosting no rectangle merges into a neighbour parcel or becomes open area.
- Envelope floors stay within what the hosted core allows: no cap with an elevator rectangle, 6 floors with the two-stair walkup rectangle, 4 with the walkup rectangle alone.
- Every envelope admits at least one floor at the minimum floor height of its type's family, mirrored from exterior's floor constants: 2.6 residential, 2.8 hotel, 3.4 offices, 3.6 corpo, 3.8 hospital and clinic, 3.0 police and military, 4.5 factory, 3.0 commerce, mall, restaurant and coffee shop.

## Depends on

- [Source partition](src/geom/partition/CONTRACT.md): retained ground ownership and exact coverage proofs.
- [Interior](../interior/CONTRACT.md): the mirrored [core-feasibility constants](../interior/schemas/core-feasibility.json) constrain parcel footprints and floor caps.
- [Exterior](../exterior/CONTRACT.md): the mirrored [floor constants](../exterior/schemas/floor-constants.json) constrain envelope floor heights.

Atlas imports no sibling runtime data. These compatibility edges keep every generated parcel buildable by the published building contracts.
